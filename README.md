# StreamLab MVP

Мінімальний застосунок для базового циклу роботи зі стрімом:

1. паралельно завантажити кілька відеофайлів із паузою, відновленням, SHA-256 і розширеними метаданими;
2. автоматично проаналізувати й підготувати stream-версію 1080p30 H.264/AAC;
3. скласти з готових файлів збережувану чергу та змінювати її порядок;
4. запустити чергу як циклічну RTMPS-трансляцію та редагувати майбутні відео без зупинки ефіру;
5. вибрати вихідний бітрейт і резервне відео;
6. підключити YouTube-канал через OAuth і контролювати сигнал та live-показники;
7. стежити за фактичним бітрейтом, FPS, швидкістю FFmpeg, відновленнями й історією подій;
8. підключити Telegram-бота з приватним меню стану, статистики, черги й сервера;
9. перейменовувати відео, зберігати іменовані плейлисти, відновлювати перервані завантаження та контролювати заповнення диска;
10. бачити live-навантаження CPU, RAM, диска й мережі та завантажувати власне PNG-прев’ю;
11. накладати WebP-промоматеріали вручну або через інтервальні кампанії без розриву RTMPS.

Це свідомо вузький MVP із входом OWNER. Черга зберігається після перезапуску.
Playout Engine запускає окремий процес відтворення для кожного відео, а постійний
uplink-процес підтримує одне RTMPS-з’єднання з YouTube.
Між ними MPEG-TS передається безвтратним локальним pipe із backpressure. Підготовлений
H.264-потік не перекодовується повторно в реальному часі: uplink лише перепаковує відео
у FLV, нормалізує аудіо та задає один безперервний часовий темп для всього ефіру.
Playout може тримати невеликий запас у локальному pipe, тому uplink наздоганяє короткі
затримки замість їх накопичення. Це прибирає залежність стабільності ефіру від піків CPU.
Коли активний промо-оверлей, кодується лише playout-відео: використовується легкий
`ultrafast` CBR-профіль із ключовим кадром кожні дві секунди; повторного encode в uplink немає.
Наступний playout запускається заздалегідь, призупиняється на перших готових пакетах і
без повторного запуску підхоплюється на межі відео; запис стану відбувається вже після
перемикання й не створює паузу в ефірі.

## Що потрібно

- Node.js 22.13 або новіший;
- FFmpeg у `PATH`, або Docker Desktop;
- RTMPS URL та stream key із YouTube Live Control Room;
- стабільний upload із запасом відносно вибраного бітрейту (налаштовується від
  3 до 12 Мбіт/с; початкове значення — 8 Мбіт/с).

`ffprobe` встановлюється разом із FFmpeg. Транскодування виконується по одному
файлу, щоб кілька великих завантажень не перевантажували сервер одночасно.

## Налаштування доступу OWNER

Скопіюйте `.env.example` у `.env`, придумайте пароль від 12 символів і згенеруйте
хеш пароля та секрет сесії. Сам пароль у `.env` не зберігається:

```powershell
$env:OWNER_PASSWORD="ваш-надійний-пароль"
npm run auth:setup
```

Перенесіть усі три рядки з результату до `.env`, а потім приберіть пароль із
поточного термінала. Не видаляйте одинарні лапки навколо згенерованих значень —
вони не дають Docker Compose інтерпретувати символи `$` всередині хешу:

```powershell
Remove-Item Env:OWNER_PASSWORD
```

`OWNER_USERNAME` за замовчуванням має значення `owner`. Не додавайте `.env` до Git.

Якщо OWNER-доступ уже налаштований у попередній версії, згенеруйте лише новий ключ
шифрування стріму й додайте виведений рядок до `.env`:

```powershell
npm run stream:secret --silent
```

## Підключення YouTube

У Google Cloud Console увімкніть **YouTube Data API v3**, створіть OAuth Client типу
**Web application** і додайте точний Authorized redirect URI:

```text
https://stream.mt-panel.sbs/api/youtube/oauth/callback
```

До серверного `.env` додайте значення без плейсхолдерів:

```dotenv
GOOGLE_OAUTH_CLIENT_ID='...'
GOOGLE_OAUTH_CLIENT_SECRET='...'
GOOGLE_OAUTH_REDIRECT_URI='https://stream.mt-panel.sbs/api/youtube/oauth/callback'
```

Після перезапуску контейнерів увійдіть у StreamLab і натисніть «Підключити YouTube».
Панель запитує лише read-only scopes `youtube.readonly`, `yt-analytics.readonly` і
`yt-analytics-monetary.readonly`: вона не може створювати, змінювати або видаляти
відео чи трансляції. OAuth-токени зберігаються у
`data/youtube-oauth.enc.json` із шифруванням AES-256-GCM. Окремий
`YOUTUBE_TOKEN_SECRET` необов’язковий; якщо він порожній, використовується
`STREAM_CONFIG_SECRET`.

Окремий YouTube API key не потрібний: запити до власного каналу, трансляцій і
stream key авторизуються OAuth access token користувача. API key не замінює цей
доступ і не додається до `.env`.

Для постійної роботи переведіть зовнішній OAuth-застосунок зі статусу **Testing**
у **Production**. У режимі Testing Google зазвичай обмежує refresh token сімома
днями, після чого канал потрібно підключати повторно.

Після підключення StreamLab автоматично використовує активний або найближчий
запланований ефір і показує поточних глядачів, перегляди, вподобання та стан
ingest-сигналу. Кнопка
«Створити RTMPS-пресет» забирає URL і stream key на сервері, зберігає їх у
зашифрованих пресетах і підставляє у форму запуску. Stream key не входить до
публічного статусу YouTube.

Live-показники зберігаються у `data/youtube-stats.json`. Детальні snapshots
утримуються 30 днів, давніші дані автоматично стискаються до одного запису на
годину. У панелі доступні діапазони 1/6/24 години, 7/30 днів, власний період і весь
час, а також окремі графіки глядачів, переглядів, вподобань, підписників, бітрейту,
CPU, RAM, вихідної мережі й показів промо. Поточний зріз можна завантажити як CSV
або структурований JSON.

Фонове опитування розподілене за бюджетом квоти: `videos.list` кожні
30 секунд, `liveStreams.list` кожні 45 секунд, `liveBroadcasts.list` кожні
60 секунд, канал кожні 10 хвилин, recent subscribers кожні 5 хвилин, YouTube Analytics щогодини,
а локальний історичний звіт — раз на добу. Базове навантаження становить близько
6672 одиниць Data API на добу. Кнопка «Оновити зараз» запускає позаплановий цикл.

Recent subscribers зберігаються за ID підписки й каналу, тому повторні API-відповіді
не створюють дублікати. Перший запит формує початкову базу без помилкового потоку
«нових» підписок. YouTube повертає лише обмежений список публічних підписників;
повний приріст, втрати й чиста зміна беруться з агрегованої Analytics-статистики.

YouTube Analytics показує середню та пікову одночасну аудиторію вибраного ефіру,
watch time, середню тривалість перегляду, gained/lost/net subscribers, likes, views
і estimated revenue, якщо канал та OAuth-дозвіл надають фінансові дані. Окрема
локальна статистика за відео рахує запуски, середню аудиторію на початку й наприкінці,
зміну аудиторії, локальний пік, інтервал перегляду, промо та playback-помилки. Ці
показники корелюють timeline StreamLab зі snapshots і не видаються за офіційний
YouTube-звіт.

Для YouTube Analytics використовуються додаткові read-only scopes
`yt-analytics.readonly` і `yt-analytics-monetary.readonly`. Вже підключений до старої
версії канал потрібно один раз відключити й підключити повторно, а scopes мають бути
додані на OAuth consent screen. Якщо monetary scope або revenue недоступні, решта
Analytics-метрик продовжує оновлюватися.

## Підключення Telegram

На екрані профілю вкажіть bot token від `@BotFather`, публічну адресу
`https://stream.mt-panel.sbs/api/telegram/webhook`, а також дозволені числові
Telegram user ID і chat ID. Для особистого діалогу з ботом ці два ID зазвичай
однакові; для групи chat ID може починатися з `-100`. Кілька ID вводяться через
кому. Після збереження надішліть боту `/start`.

Бот показує поточну та 24-годинну статистику, відео, яке зараз відтворюється,
чергу, стан сервера й трансляції. Розділ «Керування ефіром» дозволяє запустити
трансляцію через один зі збережених RTMPS-пресетів, перейти до наступного відео
або зупинити ефір. Текстові команди: `/control`, `/startstream`, `/next` і
`/stopstream`.

Кожна керуюча дія потребує окремого підтвердження. Підтвердження прив’язане до
конкретних user ID і chat ID, містить випадковий nonce, діє 60 секунд і виконується
лише один раз. StreamLab приймає webhook тільки з автоматично згенерованим secret
header; повторні Telegram update не виконуються двічі. Усі спроби й результати
керування потрапляють до журналу аудиту.

У профілі окремо вмикаються сповіщення про запуск і зупинку ефіру, втрату та
відновлення RTMPS, погіршення якості, перехід між відео, а також тривале
навантаження CPU/RAM від 90% і заповнення сховища. Перехід між кожним відео
вимкнений за замовчуванням. Сповіщення створюються з локальних подій StreamLab і
не виконують додаткових запитів до YouTube API.

Перед реєстрацією webhook StreamLab перевіряє токен через Telegram `getMe`.
Токен і секрет webhook зберігаються лише у зашифрованому
`data/telegram-bot.enc.json`; API та інтерфейс повертають тільки масковане значення.
Для шифрування використовується наявний `STREAM_CONFIG_SECRET`. Налаштування можна
також задати через `TELEGRAM_WEBHOOK_URL`, `TELEGRAM_ALLOWED_USER_IDS` і
`TELEGRAM_ALLOWED_CHAT_IDS`, але після першого підключення вони редагуються у профілі.

Після `/start` бот додає постійну кнопкову клавіатуру: статистика, поточне відео,
черга, сервер, стан трансляції, оновлення та захищене керування доступні без ручного
введення команд із `/`. Команди BotFather залишаються як альтернативний спосіб.

## Моніторинг якості

Вкладка «Моніторинг» показує машинозчитуваний прогрес постійного FFmpeg uplink:
фактичний вихідний бітрейт, FPS, швидкість і накопичене відставання подачі,
пропущені й дубльовані кадри та скидання часової шкали.
Разом зі станом RTMPS і сигналом YouTube ці дані формують один із чотирьох станів:
«Стабільно», «Ризик буферизації», «Критично» або «Ефір зупинено».

Хвилинні знімки та журнал запусків, зупинок, автоматичних відновлень і переходів
між відео атомарно зберігаються у `data/monitoring.json`. Історія обмежена сімома
днями й доступна на графіках за 1 годину, 24 години або 7 днів. Файл не містить
RTMPS URL, stream key або OAuth-токенів.

Окремий аудит фіксує всі зміни контенту, черги, налаштувань та інтеграцій. У
production він зберігається в PostgreSQL і показується у вкладці «Моніторинг».
Redis передає події між процесами, а браузер отримує їх через WebSocket; для
локальної розробки доступні файловий режим і SSE-резерв.

## Найпростіший запуск через Docker

Перед першим Docker-запуском додайте до `.env` окремий довгий пароль PostgreSQL.
У Git Bash його можна згенерувати командою `openssl rand -hex 32` і зберегти як
`POSTGRES_PASSWORD`. Після цього запустіть сервіси:

```powershell
docker compose up -d --build --wait
```

Відкрийте `http://127.0.0.1:3000`. Локальний запуск не вмикає production-профіль
Caddy, тому HTTPS-сертифікат для домену не запитується.
Next.js передає `/api` до медіасервера через внутрішню Docker-мережу, тому порт
`8788` із хоста недоступний.

### Продакшн (обидва сервіси в Docker)

`compose.yaml` запускає PostgreSQL, Redis, Caddy, Next.js і медіасервер окремими процесами. Перед стартом
контейнер готує права каталогу `data/`, а сам Node.js медіасервер працює від
непривілейованого користувача `node`.
На сервері створіть `stream-lab/.env` з `OWNER_PASSWORD_HASH`, `SESSION_SECRET`,
`STREAM_CONFIG_SECRET`, `POSTGRES_PASSWORD` та іншими значеннями з `.env.example`. Для production
використовуйте `STREAMLAB_DOMAIN=stream.mt-panel.sbs` і `AUTH_COOKIE_SECURE=true`.

```bash
docker compose --profile production up -d --wait
```

Панель буде доступна за `https://stream.mt-panel.sbs`. Caddy автоматично отримує
й поновлює TLS-сертифікат та перенаправляє HTTP на HTTPS. Резервний порт `3000`
прив’язаний лише до `127.0.0.1`, тому з інтернету недоступний.

DNS-запис `A` повинен вказувати на той самий сервер, де працює Docker Compose,
а TCP-порти `80` і `443` мають бути відкриті у firewall VPS та операційної системи.

CI/CD спочатку запускає тести, lint і production-збірку, потім публікує SHA-образи
та розгортає їх із healthcheck і rollback. Для деплою потрібні GitHub Secrets
`SERVER_HOST`, `SERVER_USER` і `SERVER_PASSWORD`.

## Запуск із локальним FFmpeg

Якщо FFmpeg не доданий до `PATH`, задайте абсолютний `FFMPEG_PATH` у `.env`.

```powershell
npm install
npm run dev
```

Команда одночасно запустить вебінтерфейс на порту `5173` і медіасервер на
порту `8788`.

## Як запустити тестовий ефір

1. У YouTube Studio створіть трансляцію через encoder. Для першого тесту оберіть
   доступ «За посиланням».
2. У StreamLab завантажте MP4, MOV, MKV, WEBM або M4V.
3. Дочекайтеся статусу «готово до ефіру». Прогрес аналізу й підготовки видно в бібліотеці.
4. Додайте готові файли до черги безпосередньо або збережіть набір у плейлисті.
5. Виберіть резервне відео та вихідний бітрейт.
6. Вставте RTMPS Server URL і Stream key або виберіть збережений пресет підключення.
7. За потреби збережіть пару URL + ключ як новий пресет.
8. Натисніть «Запустити трансляцію» та перевірте появу сигналу в YouTube Live
   Control Room.

До трьох upload-сесій передаються одночасно незалежними 8-МБ блоками. Кожен блок
перевіряється через SHA-256, а після завершення сервер обчислює checksum усього
файлу. Окремий upload можна призупинити, відновити або скасувати; незавершена
сесія переживає перезавантаження сторінки. Разом із файлом зберігаються назва,
опис, теги, тип музики, альбом, рік, профіль стиснення та правило видалення оригіналу.

Після завершення upload медіасервер збирає розширені ffprobe-метадані й рівні
гучності, перевіряє декодування початку, середини та кінця джерела, створює
уніфіковану MP4 stream-версію та повністю декодує готовий файл від початку до
кінця з жорсткою реакцією на помилки. Готовність надається лише після перевірки
H.264/AAC, 1080p30, yuv420p, 48 кГц stereo, тривалості, ненульового розміру та
SHA-256 результату. За замовчуванням оригінал видаляється лише після успішної перевірки результату.
`MEDIA_KEEP_ORIGINAL_UPLOADS=true` залишає оригінали на диску. Невдалу обробку
можна повторити з бібліотеки.

`MEDIA_ENCODER_MODE=AUTO` використовує перший апаратний H.264 encoder, який
пройшов реальний runtime-тест: NVIDIA NVENC, Intel Quick Sync, AMD AMF або Apple
VideoToolbox. Якщо апаратне кодування конкретного файла завершується помилкою,
Auto повторює підготовку через `libx264`. Режими `CPU` і `GPU` можна вибрати в
панелі глобально або окремо для кожного нового файла; явний `GPU` не приховує
помилки й не переходить на CPU без повідомлення.

Для нових файлів доступні профілі «Економний», «Стандартний» і «Якісний».
Після обробки створюється автоматичне прев’ю. Для будь-якого готового відео можна
завантажити власний PNG до 15 МБ; сервер обов’язково масштабує його до 480×270 і
конвертує у WebP. Після обриву мережі виберіть той самий локальний файл, і
передавання продовжиться з останнього підтвердженого байта.

Stream key не записується до каталогу відео. Списки пресетів повертають лише
замасковані ключі; повний ключ окремого пресету доступний лише через захищений
OWNER-метод після вибору пресету. Усі операції з відео та трансляцією вимагають
OWNER-сесію та CSRF-токен. Сесія підписана,
зберігається в `HttpOnly` cookie й автоматично завершується через 12 годин.

Пресети Server URL + Stream key зберігаються у `data/stream-presets.enc.json`,
повністю зашифрованому AES-256-GCM через `STREAM_CONFIG_SECRET`. Після запуску
ключ залишається у полі, але прихований; кнопка «Показати» тимчасово відкриває його.

Під час активної трансляції поточний елемент, бітрейт і stream key зберігаються в
`data/` лише у зашифрованому AES-256-GCM файлі. Після падіння uplink або перезапуску
контейнера ефір відновлюється автоматично з експоненційною затримкою до 5 хвилин.
Поки RTMPS-з’єднання відсутнє, playout призупиняється й продовжується після reconnect,
тому черга не прокручується вперед із втратою контенту.
Ручна кнопка «Зупинити» видаляє зашифровану конфігурацію та вимикає автовідновлення.

Черга зберігається атомарно у `data/queue.json`. До неї можна додавати один файл
декілька разів, змінювати порядок перетягуванням або кнопками, ставити елемент
наступним і прибирати окремі елементи. Усі ці операції також захищені OWNER-сесією
та CSRF-токеном. Під час ефіру майбутні елементи редагуються без перезапуску RTMPS;
поточний елемент захищений від переміщення та видалення. Кнопка «Пропустити відео»
одразу переходить далі. Після останнього відео відтворення починається з першого.

Іменовані плейлисти зберігають власний порядок відео й можуть цілком замінити
чергу, коли ефір зупинено. Видалення плейлиста не видаляє файли з бібліотеки.
Видалення відеофайла автоматично прибирає його з усіх плейлистів.

Профіль ефіру зберігається атомарно у `data/settings.json`. Під час ефіру активний
бітрейт визначається вже підготовленим stream-файлом і показується в інтерфейсі як
«Профіль поточного файлу»; це дає змогу передавати H.264 без повторного кодування.
Резервне відео відтворюється, коли звичайна черга порожня, а після додавання нового
елемента Playout Engine переходить до нього на найближчій межі відео.

У Docker структурований стан і аудит зберігаються в PostgreSQL, а JSON-файли в
`data/` залишаються локальною копією та резервним режимом без `DATABASE_URL`.
Медіафайли й прев’ю залишаються на диску сервера. StreamLab попереджає при 80%
заповнення та показує критичний стан при 90%; пороги змінюються через
`STORAGE_WARNING_PERCENT` і `STORAGE_CRITICAL_PERCENT`.

Екран «Моніторинг» отримує CPU, RAM, диск, мережу й доступні системні показники
через realtime-канал. Інтервал задає `SYSTEM_MONITOR_INTERVAL_MS` (типово 2000 мс).
На VPS температура може бути недоступною, якщо хост не передає thermal sensors
усередину контейнера. У бібліотеці кожне готове відео має компактне прев’ю 16:9.

## Промоматеріали

Вкладка «Промо» приймає PNG, JPG і WebP до 20 МБ, нормалізує їх у WebP та
зберігає в `data/promo-assets/`. Редактор 1920×1080 підтримує перетягування,
координати, розмір, opacity, safe area і готові зони. Ручний показ перезапускає
лише локальний Playout із поточної позиції; постійне RTMPS-з’єднання не
розривається. Кампанії запускають матеріал з указаною тривалістю та інтервалом у
часовому поясі `Europe/Kyiv`, підтримують паузу й зберігають кількість показів.

Кнопка «Видалити» в бібліотеці прибирає відео з черги, каталогу та фізично видаляє
оригінал, підготовлену копію і тимчасові файли. Відео активного ефіру або файл,
який ще обробляється, видалити неможливо.

## Production hardening

### Резервне копіювання і відновлення

Production-профіль запускає `backup-scheduler`: перша копія створюється після
старту, наступні — кожні 24 години. Кожен backup містить PostgreSQL dump, медіа,
прев’ю, промо, зашифровані інтеграції та стан відновлення ефіру. Незавершені
upload/temp-файли не копіюються. Архів і dump перевіряються через SHA-256,
`pg_restore --list` та читання tar; типово зберігаються останні 14 днів у
`stream-lab/backups/`.

Керування на сервері:

```bash
# створити додаткову копію зараз
docker compose --profile maintenance run --rm backup create

# показати доступні копії та повторно перевірити потрібну
docker compose --profile maintenance run --rm backup list
docker compose --profile maintenance run --rm backup verify streamlab-20260720T120000Z

# контрольоване відновлення: зупиняє web/media/backup, створює safety-copy,
# відновлює БД і data, потім запускає production та чекає healthcheck
sh scripts/restore-backup.sh streamlab-20260720T120000Z
```

Restore навмисно не запускається без `STREAMLAB_RESTORE_CONFIRMED=YES`; обгортка
встановлює його лише після зупинки сервісів. Перед перезаписом автоматично
створюється `pre-restore-*` safety-copy. Для аварії всього VPS каталог `backups/`
потрібно додатково синхронізувати на інший сервер або object storage.

Інтервал і ротація задаються `BACKUP_INTERVAL_SECONDS` та
`BACKUP_RETENTION_DAYS`.

### Reconnect-сценарії

Uplink, playout/fallback, відновлення зашифрованого стану після рестарту та replay
пропущених realtime-подій перевіряються окремим набором:

```bash
npm run test:reconnect
```

Браузер повторно відкриває WebSocket з exponential backoff до 30 секунд. Поки
WebSocket недоступний, працює SSE; `lastEventId` дозволяє дограти пропущені події,
а якщо курсор уже не зберігся, SPA одразу завантажує новий snapshot.

### Security-аудит

Локальний аудит перевіряє відсутність tracked secrets, обов’язкові environment
secrets, Docker privilege hardening, закриті внутрішні порти, backup/restore guards,
Secure cookie та security headers. Він також є обов’язковим кроком GitHub Actions.

```bash
npm run audit:security
npm run audit:security -- --url https://stream.mt-panel.sbs --report reports/security-production.json
npm run audit:dependencies
```

Production URL додає живу перевірку HTTPS, health endpoint, HSTS, CSP,
Permissions-Policy, Referrer-Policy, X-Content-Type-Options і X-Frame-Options.

### Load test

Load test виконує лише безпечні GET-запити. Без облікових даних перевіряється
`/api/health`; із `LOAD_TEST_USERNAME` і `LOAD_TEST_PASSWORD` — також бібліотека,
черга, стрім, системні метрики, моніторинг і сховище. Пароль не передається в
аргументах командного рядка й не потрапляє до звіту.

```bash
export LOAD_TEST_URL='https://stream.mt-panel.sbs'
export LOAD_TEST_USERNAME='owner'
read -s -p 'OWNER password: ' LOAD_TEST_PASSWORD; export LOAD_TEST_PASSWORD; echo
npm run test:load -- --duration 300 --concurrency 20 --max-p95 500 --report reports/load-production.json
unset LOAD_TEST_PASSWORD
```

Тест проходить, якщо error rate не перевищує 1%, а p95 базових API — 500 мс.

### Обов’язковий 72-годинний soak test

На екрані «Моніторинг» запустіть тест кнопкою «Запустити 72 години» після старту
ефіру. Стан записується у `data/soak-test.json`, тому deployment або restart
медіасервера не обнуляє прогрес. Щохвилини локально перевіряються доступність
ефіру, PostgreSQL і Redis, RSS/heap, накопичення temp-файлів та покриття сценаріїв;
жодних додаткових YouTube API-запитів тест не робить.

До завершення одного прогону потрібно побачити в картці п’ять зелених пунктів:

1. звичайний перехід між відео;
2. роботу fallback;
3. втрату й успішне відновлення RTMPS;
4. показ промоматеріалу;
5. будь-яку дозволену Telegram-команду.

Прохід вимагає щонайменше 99,5% здорових samples, не більше 30% сталого приросту
RSS, не більше 512 МБ приросту temp-файлів і всі п’ять сценаріїв. Лише фінальний
статус «Пройдено» після фактичних 72 годин закриває приймальний пункт ТЗ; короткі
unit/integration-тести не підміняють цей прогін.
